# The MIME corpus

Raw messages in, and the AUTHORED parse each must produce — in TypeScript
(`tests/mime.test.ts`) and in PHP (`php/tests/MimeTest.php`) alike. Every
`expected.json` was written by hand from the message, never captured from a
run: two runtimes agreeing proves they agree, and a parser that drifted in a
shared decision would move both together in the one place the comparison is
load-bearing.

## The shape, in key order

```
message     headers, subject, messageId, text, html, parts, attachments
header      name (lowercased), value (unfolded, RFC 2047-decoded)
part        index, contentType, charset, disposition, filename, contentId, size, headers
attachment  …part…, content (base64 of the transfer-decoded bytes)
```

## Decisions each case pins

| case | decides |
|---|---|
| `0001-plain-seven-bit` | A non-multipart message is ONE part whose headers are the message's `content-*` headers. The body keeps its own line endings; `size` is the transfer-decoded byte length. |
| `0002-alternative-quoted-printable-latin1` | The line break before a boundary belongs to the BOUNDARY, not the part. Quoted-printable soft breaks (`=` at end of line) join lines; `=XX` decodes. A Latin-1 part comes back as UTF-8 while `size` counts the Latin-1 bytes. RFC 2047 Q-words decode in `from` and `subject`, and `_` means space. The preamble is ignored. |
| `0003-mixed-base64-attachment` | An RFC 2047 B-word in UTF-8 decodes. A part with `Content-Disposition: attachment` is an attachment: its bytes come back as base64, `filename` from the disposition, `charset` null for a non-text part. `text` is the first non-attachment `text/plain`. |
| `0004-nested-inline-image-rfc2231` | Nested multipart flattens to leaves in document order with one running `index`. A folded `Subject:` unfolds, and two adjacent encoded-words join without the whitespace between them (`_` in a Q-word is a space). Every non-text leaf is an attachment even when `inline`; its `contentId` loses the angle brackets (a `cid:` reference omits them); RFC 2231 `filename*=UTF-8''…` percent-decodes; the raw header value in `headers` stays as written. |
| `0005-crlf-line-endings` | CRLF is accepted everywhere: between headers, at the blank line, in the body. A text part keeps its own line endings, so `text` carries `\r\n` and `size` counts them. GENERATED by `build.mjs` beside it, because an authored file would not survive a checkout; a test fails when the two differ. |
| `0006-unsupported-charset-then-windows-1252` | A text part in a charset this package does not decode (koi8-r) is still a part — with its `size` — but has no text and is not an attachment; `text` is the first text/plain that CAN be decoded. windows-1252 decodes its 0x80–0x9F range (“ ” €), which true Latin-1 would not. |

Things every case relies on: header names are lowercased and values unfolded
(a continuation line joins with one space); CRLF and LF are both accepted;
`messageId` is the `message-id` header verbatim, angle brackets included.
